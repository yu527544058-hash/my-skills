# AHT 目标测算

一个"该给多少时间"的问题，90% 的错误发生在算术之前——口径没对齐、基线语义搞反、把混杂因素当成了驱动因素。**先走完 0–2 步，再动公式。**

分析用 `scripts/aht.py`，它一次跑完配对检验、方差分解、目标曲线。

## help 模式

参数是 `help` / `帮助` / `用法` / `怎么用`，或者用户问这个 skill 怎么用时：**不要跑任何分析**。读取同目录的 `HELP.md`，展示给用户（可以按对话语境略作精简，但不要改成术语），最后问一句用户属于三种用法里的哪一种。

## 0 · 口径先行（不做这步后面全白算）

三个定义必须来自同一个来源，缺一个就停下来问：

| 要素 | 必须钉死的 |
|---|---|
| **长 case 阈值** | `>30`？`≥40`？`40–120`？同一批数据换个口径，占比能差好几倍 |
| **分母** | 「N 个 case」数的是**不同 Item** 还是**标注实例**？双标项目里两者差近一倍 |
| **基线语义** | 见第 2 步，这是最容易搞错的一个 |

**q 和 T_长 必须同源。** 用宽口径数出的占比，配窄口径算出的 T_长，得到的数没有意义。

## 1 · 先校验转录

用户常给截图。**复算均值规模和均值 AHT，跟表格自带的汇总行对**——对不上就是读错了，别往下走。同时核对 `占比 = 长case数 / 完成总数` 是否自洽。

图片缩放严重时（宽度压掉 3 倍以上）**不要逐行猜数字**，直接要 CSV。汇总行字号大通常还能读，但要说明哪些读了哪些没读。

## 2 · 基线语义：混合均值 还是 无长 case 基线

给定"当前 AHT = B"，两种含义算出的结果方向相反：

- **B 是实测混合均值**（已含长 case）→ 反解 `T_短 = (B − q₀·T_长) / (1 − q₀)`，再按新 q 重算。占比下降时目标**下调**。
- **B 是"完全没有长 case"的基线** → `T_短 = B`，增量纯加。占比上升时目标**上调**。

**不确定就直接问。** 这一条搞反，答案会差出几十秒且方向相反。

## 3 · 混合均值模型

```
目标 = (1 − q) · T_短 + q · T_长
     = T_短 + q · (T_长 − T_短)          斜率 = (T_长 − T_短)/100 秒/百分点
```

这是**算术，不是拟合曲线**——给定 T_短 和 T_长 它就是对的。风险全在两个输入是否稳定（见第 6 步）。

T_长 用**均值**，不是中位数——只有均值满足混合可加性。但要同时报告中位数，右偏严重时说明均值被尾部拖着。

## 4 · 找配对（这一步价值最高）

**扫一遍 Item ID 有没有重复。** 同一个 case 被两个人各做一遍 = 天然对照实验，case 难度被完全消掉，剩下的纯粹是人。

有配对就能算：
- 慢/快比的几何均值 → 人效差异的量级
- 按 Item 分组的方差分解 → 「哪个 case」vs「谁在做」各占多少
- 每个人相对**同 case 平均水平**的倍数 → 干净的个人效率，不受分派差异污染

**必问**：这是双标（两人独立做同一 case）还是一标一审？后者两个时长做的不是同一件事，倍数不能读作人效差异。判据：看有没有人固定处在"第二道"——没有则倾向双标。要定论就加开始时间戳。

## 5 · 别急着说"X 与 Y 无关"

R² 低有两种可能：真无关，或者**有个更强的混杂因素把信号淹了**。

常见情形：按规模变量分组时 R² 只有个位数，看着像"规模无关"。但同一规模内部往往有数倍的离散，其中一大块是**处理人差异**（同一个 case 换个人做，差 2 倍以上并不罕见）。把人控制住之后，规模的效应常常就变显著了。

**结论要写成「效应小于 X」而不是「无关」**，除非已经控制了主要混杂因素。

## 6 · 外推前先检验两件事

要求的 q 超出已观测范围时（比如实测 7%，问 20%）：

1. **T_短 会不会变？** 工作量整体变化时短 case 也可能跟着变。
2. **T_长 一定会变。** 占比上升若来自"整体分布右移"，新进来的都是刚过阈值的**较短**的 case，T_长 会**降**；若来自"混进了更长的批次"，T_长 会**升**。

**判据：看长 case 的平均规模往哪走。** 降 → 分布右移，T_长 调低；升 → 新批次，T_长 调高。
拿到新的 T_长 后直接代入，不要用旧的 T_长 线性外推。

有实测 T_长 就用实测的；只有规模变化时，用 `T_长_new = T_长 × exp(slope × ΔN)`（slope 从 `log(AHT) ~ 规模` 回归得到），并用「实测落在新 N 附近的 case 均值」交叉验证——两者接近才可信。

## 7 · 数据质量三查

- **单条离群点的影响**：逐个剔除最大值看均值怎么动。见过一条 3 小时的记录把几十条样本的均值抬高近 10% —— 而同一个 case 另一个人只用了十几分钟。超长记录多半是挂机而非真实工时，没有时间戳无法证实，但必须标注出来。
- **缺失值的方向性**：比较缺失行和有值行的规模均值。若缺失偏向长的一端（最耗时的 case 恰好没数），T_长 就是**低估**。
- **删失数据**：`deferred` / `In check` 直接丢掉会系统性低估成本，要单独说明去向。

## 8 · 最后做量级对比

给出目标值之后，**把这次调整的幅度和其他方差来源放在一起比**：

> 本次调整 +20%　vs　同 case 换人的效率差 2 倍以上

如果调整幅度远小于未处理的噪声，要明说：这个数适合做**产能规划**（排产、估人力、算成本），但不适合直接当**个人考核线**——会有相当比例的人因为人效差异而非努力程度不达标。个人考核需要先按人设基线。

同时给出**动态形式**而不是单个数字，免得占比一变就要重拍：

```
当日目标 = T_短 + 斜率 × 当天实际长 case 占比(%)
```

## 怎么跑 scripts/aht.py

CSV 至少需要 AHT（时长）一列，规模变量可选；有 Item ID 和标注员列时自动做配对分析。列名自动识别，识别不到用 `--cols worker,item,seg,aht` 按位置指定（无此列填 `x`）。`deferred` / `In check` 等非数值自动剔除并单独统计。

```bash
# 基线是「无长 case」时的值
python3 scripts/aht.py data.csv --baseline 500 --baseline-is short \
        --q 0.10 --q 0.20 --expect-aht 1450

# 基线是含长 case 的实测均值（必须给 --q0）
python3 scripts/aht.py data.csv --baseline 500 --baseline-is mixed --q0 0.10 --q 0.07

# 有更新的实测 T_长 时覆盖掉文件里算出的
python3 scripts/aht.py data.csv --baseline 500 --baseline-is short --t-long 1900 --q 0.20
```

`--expect-seg` / `--expect-aht` 传表格自带的汇总值，脚本会复算比对——**转录校验就是这一步**。

输出先给【结论】和【需要注意】，后面是详细数据：数据概览 → 核对表格汇总（给了 `--expect-*` 时）→ 同一个 case 换人做差多少 → 每个人的快慢 → 规模的影响 → 特别慢的记录 → 目标怎么算。**自己分析时加 `--tech`**，会多显示 R²、t 值、几何平均这些统计细节；默认不显示，免得用户自己跑时被吓到。转述给用户时照样要翻译成大白话。

## 连续规模变量：试标定标 → 生产重标 → 每批出目标

用 `scripts/calib.py`。"规模"指这个项目里什么越多、处理就越费时：视频看**时长**（或 **segment 数**），文本看**字数**，图片看**张数**。**先确认用户的项目是哪一类，不要默认是视频。**

模型用大白话讲：**每条处理时间 = 起步时间 + 每单位多花 × 规模**，就像打车费 = 起步价 + 每公里的钱。跟用户说明时用项目自己的话：视频说"每秒多花"，文本说"每 100 字多花"。不要说"截距 / 斜率 / 固定开销"。

**不要只凭"平均 AHT + 平均规模"按比例缩放。** 那等于假设起步时间为 0：短的批次会少给，长的批次会多给。

| 阶段 | 用户给 | 命令 | 产出 |
|---|---|---|---|
| 1 定标 | 项目经理试标（≤30 条）：case ID、规模、AHT、标注顺序 | `calib.py fit trial.csv --warmup N --prod-mean X --save pm.json` | 起步时间、每单位多花、基线 |
| 2 重标（必做） | 上线 2–3 天的生产逐条数据，带标注员 | `calib.py fit prod.csv --vs pm.json --save prod.json` | 生产模型 + 项目经理→标注员换算系数 |
| 3 每批 | 这批的平均规模（或规模列表） | `calib.py predict --model prod.json --mean X` | 本批目标，超出定标范围会提醒 |

要点：

- **单位按列名自动识别**：视频时长 / duration → 秒（支持 `mm:ss`），字数 / 字符数 / 文本长度 → 字，图片数 / 张数 → 张，segment → segment。认不出或认错时用 `--unit 字 --label 字数`
- 每单位多花很小时（如每字 0.12 秒），输出会自动换算成"每 100 字多花 12 秒"这种好读的说法
- **试标要短、中、长都挑**，最长至少是最短的 2 倍。30 条以内时，覆盖范围比条数重要
- **前 3–5 条是热身**，用 `--warmup` 去掉。不确定就先不加参数跑一次，脚本会自动检测
- **项目经理只有一个人时，阶段 2 不能省。** 试标给的是项目经理的水平，和标注员可能差很多。算出的换算系数存进模型，下个项目只有试标时用 `predict --ratio` 先顶上
- **兜底**：规模能解释的差异不到 30% 时，脚本自动改为统一平均值。如果是试标跨度太窄导致的，会单独说明"看不出影响 ≠ 没有影响"
- 起步时间算出负数时，自动改为完全按比例（样本少时常见）
- 线性模型下，批次目标只取决于这批的**平均规模**；要逐条目标才需要完整列表（`--per-case`）

## 用在别的项目上

模型只需要「短 case + 长 case + 长 case 占比」，跟标注没关系。换项目时做一次词汇映射即可：

| 抽象角色 | 你的项目里对应什么 |
|---|---|
| 规模变量 | 任何驱动成本的量：segment 数 / 字数 / 图片数 / 视频时长 / SKU 数 / 附件数。**没有也能跑**，只是少了「时间花在哪」的拆解 |
| 长 case | 按项目自己的规模定：超过多少字、多少张图、多长的视频 |
| 处理人 | 标注员 / 客服 / 审核员 / 质检员 |
| Item ID | 工单号 / 任务 ID —— **只要有重复就能做配对**，这是最值钱的一步 |

列名别名表在 `scripts/aht.py` 顶部的 `ALIAS`，加自己的列名进去即可；用 `--size-label 字数` 让输出说项目自己的话。

**最低输入（只要目标数字）**：基线 B + 它的语义、长 case 占比 q、长 case 平均时长 T_长。三个数就能算。
**要诊断价值**：再给 case 级明细（每行一个 case：规模、时长、处理人、Item ID），并**原样保留** deferred / 未完成 等非数值。

## 什么时候这套方法不适用

- **成本不是二分的**：如果 case 时长是连续谱而不是"长/短"两类，两档混合均值太粗，改成多档或直接按规模变量建模。
- **分布双峰**：两种完全不同的任务类型混在一个池子里时，均值没有意义，先拆池。
- **没有重复 ID**：配对分析做不了，「人 vs case」分不开，只能给目标值不能给归因。这时别下"某某因素是主因"的结论。

## 输出建议

**跟用户说话用大白话。** 用户多半是运营或项目经理，没有统计背景。说"长 case 平均每条 X 秒"，不说 T_长；说"规模能解释时间差异的 6%"，不说 R²；说"时间差异里一半来自换人"，不说方差分解、组间组内；说"真实值大概率在这个范围"，不说置信区间；说"一般来说慢的人是快的人的 2 倍"，不说几何均值。脚本输出里的术语要翻译后再转述，不要原样贴给用户。第一次提到 AHT 时说一句"平均每条处理时长"。

结论先行，然后是推导，最后是存疑项。数字要带区间和样本量。若要做成可分享的页面，用 Artifact，图表加 PNG 复制按钮（导出时强制浅色，文档编辑器多为白底）。

改口径或来新数据时**重跑整条链**，不要只改最后那个数字——T_长、斜率、配对结论会一起动。
